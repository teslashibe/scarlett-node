# scarlett-node

Outbound-only, independently built supplier client. This is an early runnable **protocol proposal**, not a deployable marketplace node until the coordinator implements `api/node-v1.openapi.yaml`. No private app imports or hosted provider credentials are needed. Provider subscription terms and permission to relay paid inference are separate from this implementation and must be checked before serving real jobs.

Build: `go build -o scarlett-node .`; test: `go test ./...`.

Configure `SCARLETT_COORDINATOR=https://...` (HTTPS origin), `SCARLETT_GATEWAY=http://127.0.0.1:PORT` (loopback HTTP or HTTPS origin), `SCARLETT_MODEL=...`, `SCARLETT_PROFILE=...`. Optional `SCARLETT_GATEWAY_KEY` remains local, `SCARLETT_STATE_DIR` defaults to `~/.local/state/scarlett-node`, `SCARLETT_INFERENCE_TIMEOUT_SECONDS` defaults to 45 (max 300), `SCARLETT_MAX_INPUT_BYTES` defaults to 32768 (max 65536), `SCARLETT_MAX_OUTPUT_TOKENS` defaults to 2048 (max 8192). Supply a locally managed OpenAI-compatible gateway with `/v1/chat/completions`, non-streaming chat, `max_tokens`, exact resolved `model`, and `usage.prompt_tokens`/`usage.completion_tokens`. `open-agent-api` advertises `/health/ready`, `/v1/models`, and chat completions. **Its current chat request struct does not define `max_tokens`, so the field sent by this node is ignored and is NOT an upstream cost ceiling.** The node checks reported completion tokens after inference and rejects over-budget results, but cannot bound billed tokens ahead of time with this gateway. Its real subscription auth and response usage behavior still need a live integration check. No gateway URL comes from jobs.

Run `./scarlett-node pair` and enter a one-time coordinator code on stdin. Pairing creates a private `identity.json` (0600) under a 0700 state directory; run `./scarlett-node run` for outbound heartbeat polling and serial inference. Pairing is non-interactive stdin (avoid shell-history exposure); the coordinator is responsible for generating and expiring codes. Configure externally managed secrets without logging them. No inbound port or wallet key is used.

For an **unpaid Docker fixture only**, `../scarlett-app/compose.yaml` builds this node twice with `SCARLETT_LOCAL_FIXTURE=1` and `local-fixture` profile. It polls the local app over Docker Desktop host loopback, skips pairing only in this explicit mode, and uses the app's temporary fixture key (not a supplier credential). Each model calls its own isolated gateway container, which read-only mounts just the existing matching account; account credentials are never mounted into the nodes. This fixture is not provider authorization and cannot cap upstream inference usage because the Codex gateway ignores `max_tokens`.

Current gaps against [issue #1](https://github.com/teslashibe/scarlett-node/issues/1): coordinator pairing, auth, committed signed job IDs and atomic lease/fence settlement are not available or validated here; no server interoperability proven. No install script, systemd unit, CLI lifecycle/status, graceful drain protocol, durable submission journal, replay-safe ambiguous submit reconciliation, signed challenge proof, dynamic capacity or independent tokenization. The worker sends no rewardable result for missing usage, model mismatch, invalid finish reason, or expired lease; it reports a failure code. Conservative transport failures may leave attempts unresolved; coordinator must time out and fence them. A byte bound is not a tokenizer; the coordinator's max-input-token constraint is checked against *actual gateway usage after inference*, not preflight. Run only in a trusted local environment until these gaps are closed.
