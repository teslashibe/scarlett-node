# Install the community node

Bundles include the Go node and pinned Rust proof helper, the pinned local browser-login helper, plus the Codex templates and a Linux user-service template. Supported build targets are Linux amd64 on Ubuntu 24.04, macOS arm64 and macOS amd64. Other Linux distributions have not been validated. Native CI uses the corresponding [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). No release or production dispatch is enabled by building a bundle.

Download the bundle for your platform and its archive checksum from the reviewed repository release or CI artifact. Verify the archive before extracting it with `sha256sum -c BUNDLE.tar.gz.sha256` on Linux or `shasum -a 256 -c BUNDLE.tar.gz.sha256` on macOS. These checks detect corruption; their trust comes from the source where you obtained them. Private repository downloads require repository access.

Extract the archive, enter its directory and run `./install.sh`. It verifies the fixed bundle files, installs a version under `~/.local/lib/scarlett-node/versions/`, and switches the active version atomically. Both executables are linked from `~/.local/bin/`; add that directory to PATH. Reinstalling the same version is allowed only when its contents match. An unrelated executable is never overwritten. You can pass an absolute installation root and bin directory as the two arguments.

Copy `node.env.example` to `~/.config/scarlett-node/node.env`, keep it private with mode 0600 and edit the absolute local credential paths, chosen services and coordinator/verifier addresses. The verifier placeholder deliberately cannot serve work. Its certificate must match the configured hostname; for a private test CA, configure an absolute `SCARLETT_VERIFIER_CA_FILE`. TLS failures stop execution. X accepts an existing private session file or interactive browser login through `scarlett-node accounts login-x`. Native bundles include the helper beside the Go executable, so no resource-path environment variable is needed. Install Google Chrome at the fixed platform path documented in [the browser runtime guide](https://github.com/teslashibe/scarlett-node/blob/main/docs/x-browser-runtime.md); missing prerequisites return unavailable. Login never downloads or searches PATH for a browser. Your provider sessions stay local. Supply any of Codex, X and web (`codex`, `x_read`, `web`); remove the unused services from `SCARLETT_SERVICES`. Web needs no credential path. In a shell, export the settings before using `scarlett-node pair` and its hidden prompt, then `scarlett-node run`.

Bundles also carry the web browser runtime (`web-runtime-<platform>.tar.gz` and `web-runtime.json`), which the installer verifies with the other bundle files. With `web` in `SCARLETT_SERVICES` the node extracts it into its state directory on first start and downloads the pinned Chrome for Testing build itself; the heartbeat reports `browser_downloading` until both are verified. You install nothing for this on macOS. `scarlett-node web-runtime check` verifies the installed runtime without pairing. On Linux two host settings can block the browser, and each needs a one-time root fix:

- `deps_missing`: Chrome's shared libraries are absent. Installing `google-chrome-stable`, the X login prerequisite above, brings them.
- `sandbox_unavailable`: unprivileged user namespaces are blocked, as Ubuntu 23.10 and later do through AppArmor. Add an AppArmor profile that grants `userns` to `<state>/web-browser-bin/*/chrome-linux64/chrome` (replace `<state>` with your node state directory) and reload AppArmor. The node never runs the browser without its sandbox. Set `SCARLETT_WEB_BROWSER=off` to run web without the browser tier instead.

Optional: captcha solvers for the browser tier, paid by you. Put each provider's key alone in a file only you can read (`chmod 600`), then set `SCARLETT_WEB_SOLVERS` (a comma list of `capmonster`, `capsolver` and `2captcha`) and, for each one, `SCARLETT_WEB_SOLVER_CAPMONSTER_KEY_FILE`, `SCARLETT_WEB_SOLVER_CAPSOLVER_KEY_FILE` or `SCARLETT_WEB_SOLVER_2CAPTCHA_KEY_FILE` to the file's absolute path in `node.env`. `SCARLETT_WEB_SOLVER_MAX_USD_PER_DAY` (default 1.00) caps the estimated daily spend. The keys stay on this machine and go only to their provider; see [the reference](https://github.com/teslashibe/scarlett-node/blob/main/docs/REFERENCE.md#browser-tier).

For the default Linux installation, copy `scarlett-node.service` to `~/.config/systemd/user/`, run `systemctl --user daemon-reload`, then `systemctl --user enable --now scarlett-node`. Pair first using the same configuration and state directory. The installer does not start services or change login persistence. Custom installation paths need corresponding edits to the unit. On macOS, run the node in the foreground or use your own process supervisor.

Every setting, readiness state and failure code is described in the operator guide at <https://network.scarlett.ai/docs/>, including running a web node on a cloud server through `SCARLETT_WEB_EGRESS_PROXY`.

## Updates

`scarlett-node update check` reports the installed and latest release, whether the coordinator still offers this version new jobs, and the release's highlights with a link to the changelog at <https://network.scarlett.ai/changelog/>. `scarlett-node update apply` installs the latest release:

1. It downloads the signed bundle for this platform from `https://network.scarlett.ai/downloads/` (or your `SCARLETT_COORDINATOR` origin; HTTPS only) and checks its length, SHA-256 and minisign signature against the keys built into the node. Nothing runs before all three pass.
2. If the node is serving, it pauses new work (`drain`) and waits until the node reports `draining` with no accepted job in flight. It never stops accepted work; after 30 minutes it resumes and gives up.
3. It runs the new bundle's own `install.sh`, which checks every file again and switches `current` atomically.
4. It starts the new binary, then restarts `scarlett-node.service` when that user service is active and waits up to three minutes for the node to report running on the new release. If either check fails, it reinstalls the previous version with that version's `install.sh`, restarts it and records the failed version.
5. It resumes new work if it was the one that paused it.

The updater finds the bin directory from the `scarlett-node` link you ran (the one this `install.sh` made); pass `--bin DIR` when you run the binary some other way and installed with a custom bin directory. `scarlett-node update rollback` reinstalls the version that was active before the last update, after accepted jobs finish in the same way. The updater works only for installations made by this `install.sh`; it refuses anywhere else.

Automatic updates are opt-in. Copy `scarlett-node-update.service` and `scarlett-node-update.timer` to `~/.config/systemd/user/`, run `systemctl --user daemon-reload`, then `systemctl --user enable --now scarlett-node-update.timer`. The timer checks about once an hour. With `SCARLETT_AUTO_UPDATE=install` in `node.env` it installs as above: a required update (one the coordinator no longer gives new jobs) installs at the next check, and an optional one at this node's fixed place in a four-hour rollout window, so the network never drains at once. Without it (the default `notify`), the timer only logs what is available (`journalctl --user -u scarlett-node-update`). On macOS, run `scarlett-node update apply` yourself or from your own supervisor.

To update by hand instead, drain, wait for zero in-flight work and stop the node, run the new bundle's `install.sh`, then restart with the same state directory. Drain persists; use `scarlett-node resume` when ready. To roll back by hand, rerun the previous version's `install.sh` with the same installation paths. Keep the identity and attempt journal throughout upgrades and rollbacks; unresolved attempts must reconcile with the coordinator before further work. Local status is an observation, not proof acceptance or payment settlement.
